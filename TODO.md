## Break-even stop management

- [x] **Narrow-only stop moves:** once the market has travelled `breakEvenTriggerPoints` in favour of a trade Signal Desk opened, its stop is moved to entry plus `breakEvenOffsetPoints`. Distances are MetaTrader points aligned onto the symbol `tickSize` (a buy rounds down, a sell rounds up); a stop is never widened and a position already at least as protected is marked handled.
- [x] **Broker rules respected:** `stopsLevel` and `freezeLevel` are checked before any request, so a stop that is too close to the market is deferred and retried instead of rejected; the decision always uses a fresh synchronized quote and the live position from the terminal state, and fails closed on crossed or missing prices, a missing specification, or an unrecognized position direction.
- [x] **Persisted per position:** `break_even_moves` keeps one row per broker position (status `moved`, `already_beyond`, `closed`, `deferred`, `failed`, `unknown`, the previous and new stop, the quote used, attempt count, next retry, and the sanitized provider message). Terminal statuses are never retried; a deferral retries without consuming an attempt while a broker rejection retries up to ten times; `unknown` never retries because the broker may already have applied the change. `TRADE_RETCODE_NO_CHANGES` counts as protected, and the recorded `trades.stop_loss` follows the broker.
- [x] **Same loop, never in the way:** the sweep runs in the execution worker after an idle tick, and every fifth iteration while orders are being processed so a busy signal stream cannot starve protection, throttled by `BREAK_EVEN_SWEEP_INTERVAL_MS` (default 5000 ms, floor 1000). Auto-Trading off, an account change, an undeployed account, or the runtime switch all stop the request before it reaches MetaAPI; only outcomes the broker actually answered consume an attempt; changing a distance re-arms handled positions.
- [x] **MetaAPI surface widened once:** the trading adapter now calls the SDK's `modifyPosition(positionId, stopLoss)` only (no take profit is ever sent, so the existing take profit survives) and keeps the provisioning/user token server-side. No close, partial close, or pending-order capability was added.
- [x] **Settings and UI:** `GET/PUT /api/settings` carries `breakEvenEnabled`, `breakEvenTriggerPoints`, and `breakEvenOffsetPoints` with server-side bounds; Risk settings gains a Break Even section that states the scope and that Auto-Trading off also stops these moves, and each trade row shows its break-even outcome and reason. The required live-trading warning text is unchanged.

**Break-even validation:** backend suite passes 150/150, with 27 new tests for the decision function (trigger, both sides, tick alignment, never-widen, stops/freeze deferral, fail-closed inputs), failure classification (deferred vs rejected vs ambiguous), and the sweep (runtime gate, throttle, re-check before the write, closed positions, `NO_CHANGES`, provider rejection sanitized without the token, unsynchronized account, worker ordering, and a failing sweep not taking the loop down). ## True trailing stop on top of break even

- [x] **One sweep, one rulebook:** the trailing stop is not a second job. `sweepBreakEven()` now computes both targets — entry + offset for break even, and market − distance for the trail — and takes whichever is **more protective**, so turning trailing on can never weaken break even and vice versa. Settings are `trailing_stop_enabled` and `trailing_stop_distance_points` (default 10 points, validated 1-100000 server-side, never clamped).
- [x] **The three guarantees held:** a stop only ever moves tighter, so a retracing market yields `wait` rather than a loosening write (and `already_beyond` becomes a `wait` while a trail is running, because a trail is a standing instruction, not a one-off job); every decision reads the price, the position's live stop, and the symbol specification from a single synchronized account read, with `waitForFreshPrice` refusing a stale quote; and `unknown` from `classifyBreakEvenFailure` still means no scheduled retry — `unknown` and `closed` rows are never re-offered to the sweep, so an unconfirmed move can never be resent.
- [x] **Ledger that survives repetition:** `break_even_moves` keeps exactly one row per broker position and adds `move_count` and `trailing_distance_points`; the write guard that made a terminal row untouchable now admits a `ratchet` write only for a workspace with trailing on, so break even's one-write-per-position behaviour is byte-for-byte unchanged while a trail can keep updating its own row. Candidate selection re-includes `moved`/`already_beyond` rows only when trailing is enabled and no new query parameter was needed, keeping the throttles (`BREAK_EVEN_SWEEP_INTERVAL_MS`, sweep limit, `stopsLevel`/`freezeLevel` backoff, ten-attempt cap) in force for both.

## What a captured message means, and how it can be removed

- [x] **Suspend now says what the backend said - and so does the backend.** The refusal sentences from `PATCH /api/admin/users/:id` reach the panel unchanged, and a refused account edit is no longer invisible: the server logs `Admin account edit refused` with the actor, the target, the status, and the field *names* that arrived, and a refused suspension writes `user.suspension.refused` to `admin_audit_logs`. A successful one logs which columns actually changed. The class of bug this closes was the silent one - a form that looked busy and did nothing, with no request and no log line to find later.
- [x] **The GramJS listener stopped being silent, which is how the drop was found.** Monitoring compared `channels.channel_id` with one string derived from one accessor (`message.chatId`), so whenever Telegram handed the other spelling of the same channel (`-100…` against the bare id) every message failed to match and was returned unhandled, with no row, no error, and nothing in the log while manual entry kept working. `server/services/telegram-peer.js` now owns that boundary: `resolveTelegramChatId` tries the message, its `peerId`/`chatPeer`, the event's `update`/`chatPeer`, `toPeer()`, `toObject()`, and Long-style stringification before concluding nothing; `telegramPeerIdVariants` produces every spelling a row could hold and the lookup matches with `channel_id = ANY($2::text[])`. Basic-group ids are matched, never rewritten, because canonicalising `-7` to `-1007` invents a chat. `telegramMessageText` reads text or a media caption, strips the zero-width marks Telegram scatters through channel posts, and caps the payload at 4000 characters - invisible padding was also breaking the header regexes. **Every** update is then logged with its outcome (`captured`, `ignored: that chat is not monitored`, `carried no text to read`, `had no chat id to match on`), the parse/save is wrapped so a storage failure is logged instead of swallowed, and unparsed or refused messages are stored anyway because a capture is not a reward for parsing cleanly. `GET /api/telegram/status` reports `listening`, `messagesSeen`, `signalsSaved`, `lastMessageAt`, `lastChatId`, `lastError`, and `monitoredChannels`, and re-attaches a missing handler when it finds a connected client with none - the failure mode itself, made visible and self-repairing.
- [x] **An unread signal explains which part it is missing.** `parseSignal` returns the same seven fields plus `directionInferred`, `hasTradingData`, `missing: {entryPrice, stopLoss, takeProfit}` and a `blockers` array (one code and one sentence each), and `parseError` is the first blocker's message, so every sentence the app has always written is still exactly the same text. A direction is inferred only when the message states none at all, an entry and exactly one target exist, and the two differ - and the inference immediately adds its own blocker, so an inferred direction can be read but never traded. `SELL XAU/USD` with a stop and no target was executable before and still is: a target is for reading, never an eligibility rule, and that asymmetry is now a test. The panel shows **Inferred**, **Missing SL**, and **Missing TP** badges, and "No clear signal" is reserved for a message that said nothing about a trade - a legible note missing one price reads "Needs review" with the server's sentence under it.
- [x] **Advanced Safety: a workspace can now decide whether a stop-less signal may execute.** `settings.block_execution_without_stop_loss` (boolean, `DEFAULT TRUE`, added by the app's own idempotent startup migration) is read by `GET /api/settings`, written by `PUT /api/settings` where an absent value means on, read at capture time to decide `execution_ready`, and read by the engine at claim time. Risk settings were regrouped into **Core Risk**, **Trade Management**, and a closed **Advanced Safety** disclosure whose summary says `Blocking`/`Allowed` before it is opened. Off permits an SL-less signal only in **Fixed Lot** mode - risk-based sizing divides by the distance to a stop that would not exist, and those signals are refused with that reason. Nothing else relaxes: plan, runtime, kill switch, freshness, explicit direction, and account state all still apply. Fixing the gate also exposed an older defect: the claim query read `Number(item.stop_loss)`, and `Number(null)` is `0`, which is finite and on the correct side of any price - so a signal with no stop was never actually blocked there, it was sent to the broker and stored as a stop at **0**. Null and 0 are told apart before anything is decided, `undefined` goes to MetaAPI, and `null` goes to the trade row.
- [x] **Signal history is deletable, and trades are not.** `DELETE /api/signals/:id`, `DELETE /api/signals`, `DELETE /api/admin/signals/:id`, `DELETE /api/admin/users/:id/signals`, `GET /api/admin/signals/purge-preview` and `POST /api/admin/signals/purge` (default 30 days) all run one statement *pair* in a single transaction borrowed from the pool: `UPDATE trades SET signal_id=NULL …` then `DELETE FROM signals … RETURNING id`. The user's own delete binds the owner inside the statement (`WHERE id=$1 AND user_id=$2`) so RLS is not the only thing confining it to their rows, `signals` has no cascade that could reach a trade, `execution_jobs.signal_id` is `ON DELETE CASCADE` (a queued order dies with the signal, which is what "I do not want that signal" means, and both dialogs say it), and the admin purge ages with `NOW() - ($1::int * INTERVAL '1 day')` written once per pair so a preview cannot disagree with the delete it previews. ## A trade is never naked because the provider forgot

- [x] **Fallback Safety Nets: the workspace can supply the leg a signal omitted, in points.** `settings.fallback_stop_loss_points` and `settings.fallback_take_profit_points` (`NUMERIC`, nullable — no row value means no net) are added by the app's own idempotent startup migration, read by `GET /api/settings`, written by `PUT /api/settings` through `readFallbackPoints` (a whole number in `1…1000000` or blank, anything else answered by one sentence naming the field, never clamped), read at capture time to decide `execution_ready`, and read by the engine in the same query that claims the job. The order is fixed: the signal's own value, then the fallback, then the block — so a level the channel stated is never overwritten, and a trade completed by a net is not an override and never logged as one.
- [x] **A fallback is priced against a live quote, not against the signal's stale entry.** `applySafetyNets` computes `order price ∓ points × tickSize` and aligns onto the broker's tick grid *away* from the market (down for a buy's stop, up for its target, mirrored for a sell), so a rounding step can neither tighten risk nor land inside `stopsLevel`. A stop is judged against the price the position is valued at and a target against the price it has to beat, because reusing one rule for both made a correct 4000-point target look unusable. `signals.execution_note` then says the level came from the workspace — with `above`/`below` written for the side actually traded — and an executed job is allowed to leave that explanation behind it, which is why `updateJob` gained a note argument rather than a special case.
- [x] **`Block execution if Take Profit is missing` is the other half of the guard, and it is on by default.** `settings.block_execution_without_take_profit` (`BOOLEAN NOT NULL DEFAULT TRUE`) refuses a signal with no target — a position with nothing planned to close it used to be the one thing this app would happily open. It is independent of the stop block, and the folded summary reads `Blocking` while either stands. An override is only reachable with the block off *and* no fallback, and says so: `Trade executed without Take Profit (User Override).` on the log line, with the user, job, signal, symbol and account in the same JSON record, and on the signal row.
- [x] **A net that cannot be honoured is reported, not dropped.** No tick size for the symbol, a distance inside the broker's `stopsLevel`, a result at or below zero, or a leg too small to clear the spread each produce `*-net-unusable`, and the block then applies to that leg as if no fallback existed — with both facts in the one sentence the user reads ("…the broker requires stops at least 50 points from the market, and the fallback distance is 10"). Quietly ignoring a setting somebody configured is how a "safe" workspace ends up trading without the stop it believes it asked for.
- [x] **One policy, two questions, and the `Number(null) === 0` trap closed for good.** `server/services/signal-safety.js` holds `captureSafety` ("may this message be queued at all?") and `applySafetyNets` ("what prices go on this order?"), and `index.js` and the engine both ask it instead of restating the rule; `isBlockedOnlyByStopLoss` and the capture-side `allowMissingStopLoss` expression are gone, because two copies of a safety rule is how a signal got stored as executable and then refused, or stored as refused and then traded. Absence is tested with `statesPrice` before any conversion, so `null`, `undefined` and `''` are all "the leg does not exist" and none of them is 0.
- [x] **Risk settings copy extended, not rewritten.** The three controls are in the same folded **Advanced Safety** group under the existing sentences: two block toggles, then `Fallback Stop Loss (points)` and `Fallback Take Profit (points)` (blank field, `None` placeholder, help text saying the channel's own value always wins and that an unusable distance is reported rather than ignored). The two lines that the new toggle made untrue were corrected — the badge titles for **Missing SL** / **Missing TP** no longer promise that a missing target can never stop an order, and one bullet now says the block, not the parser, decides.

## The advanced page folds into three bars, and a numbered target list becomes a trade plan

- [x] **Advanced Settings is three folded bars, each stating its own state.** `client/src/components/SettingsSection.jsx` is one `<details>` element with a light header bar, a chevron that rotates on the browser's own open state, the section title and a one-sentence summary, and a badge for what the group is currently doing (`Auto-Trading OFF`, `No stop moves · First Target Only`, `Blocking`). **Core Execution** (open by default) holds the Auto-Trading toggle, the connected trading account and the lot size — the three things that decide whether an order exists at all and on what account; **Trade Management** (closed) holds break even, the trailing stop and the new **Multiple Target Handling** dropdown; **Advanced Safety Nets** (closed) holds the two blocks and the two fallback distances. Every control kept its `id`, its `min`/`max`/`step`, and its copy, so a reader who learned where a value lives can still find it; nothing longer than one sentence stays outside a bar. Folded markup is still rendered markup, so every sentence the panel's tests quote is asserted exactly as before, and `test/signal-review-ui.test.mjs` now pins the fold itself: one bar open, three chevrons, three one-sentence summaries, and the account/lot selectors sitting with the switch rather than with the trade.
- [x] **Several targets are a plan, and the workspace chooses what to do with it.** `settings.multiple_target_handling` is `first_target` (default, and what every workspace did before this existed), `final_target`, or `scale_out`, and `signals.take_profit_levels` stores the whole ladder the parser read so an execution can never disagree with the row a human reviewed. All the policy — which price the position carries, which levels are swept, what share each closes, whether a slice survives the broker's minimum lot — lives in `server/services/scale-out.js`, which never touches a broker: the engine asks it what to send and the sweep asks it what to close, so both answers are testable without a connection. Scale-out opens the full size with the **final** target on the position and writes one `trade_tp_levels` row per earlier target (50% then 30%, a fifth of the position riding; 50/50 for two targets; the 80% budget shared evenly beyond three). A trade too small to split keeps its first target and gets no plan rows, and a level whose price the channel wrote out of order, or on the wrong side of the quote, is dropped with the reason recorded rather than renumbered into a plan nobody described.
- [x] **A sweep banks each target and moves the stop in the same pass, and it cannot do either twice.** `sweepTakeProfitLevels()` reads one synchronized account snapshot per account and symbol, claims a level row to `submitting` before the call, closes only what the live position can legally spare (`resolveCloseVolume` keeps the remainder at or above the symbol minimum and prefers closing everything the plan asked for over leaving dust), then moves the stop to break even through the same `calculateStopGuard` the break-even sweep uses — so it can only ever tighten, honours `stopsLevel`/`freezeLevel`, and still lands in `break_even_moves` where the panel already reads stop moves. A refusal that is a broker condition defers on the existing clocks; a size that can never be legal is settled as `skipped`; an ambiguous provider answer is `unknown` and is never re-offered, because a second close would be a trade nobody asked for; a claim left in flight by a dead process is settled as `unknown` after five minutes. The close and the stop move have separate retry state on the row, so a refused stop move retries the stop move alone.
- [x] **The plan is visible where the trade is.** `trades.remaining_volume` is set when a plan is attached and updated with each close, so it states what is open now, and stays `NULL` on a trade that never had a plan, `GET /api/trades` returns it with the level rows, and the activity list says `0.1 lots · 0.05 lots left` and `Scale-out: 1.12 closed (50%) · 1.15 being closed`. `unconfirmed` is spelled out rather than softened. `signals.execution_note` carries the plan as it was made, so a trade row can still be read after the plan rows are long gone.
- [x] **Both refusals stay refusals.** A scale-out plan is not a licence to trade something the safety rules rejected: the signal still needs a stored direction, a symbol, an execution-ready parse, the workspace's blocks and a managed deployed account, and the entry price still guards the send. `scale_out` also needs the execution runtime, and `PUT /api/settings` answers with `409` rather than storing a mode nothing will sweep. A platform pause holds new orders and does not hold the sweep, because closing a target and moving a stop to entry reduce exposure — the same reasoning break-even moves follow.
- [x] **The boundary between the panel and the engine is pinned on both sides.** `test/scale-out-settings-ui.test.mjs` reads `TARGET_MODES` out of `server/services/scale-out.js` and requires the dropdown's three values to be exactly those, in that order, because a mode the panel could offer and the engine could not read would be a setting that quietly does nothing; `settings-navigation-ui.test.mjs` still derives every writable field from the route itself, which is how `multipleTargetHandling` had to arrive with its server-side validation and its `set('…')` owner in the same change.
- [x] **The schema arrives the way the rest of this app's schema does.** `signals.take_profit_levels`, `settings.multiple_target_handling` (with its `CHECK`), `trades.remaining_volume` and `trade_tp_levels` are idempotent statements in `initializeDatabase`, RLS enabled on the new table like its neighbours, with `UNIQUE(trade_id, level_index)` as the idempotency key and a partial index on the statuses a sweep reads. No migration file, no destructive statement.

**Validation:** `server` 383/383 (new `test/scale-out-plan.test.js` for the ladder arithmetic and the volume rules, new `test/scale-out-sweep.test.js` for the order the engine sends, the plan rows it writes, and the sweep cases against a mocked adapter — every "exactly once" claim in this feature is a call count on that fake, not a description; `test/metaapi-trading.test.js` pins `closePositionPartially(positionId, volume, options)`; `test/signal-safety.test.js` extended so the nets, the ladder and the mode travel in the one query that claims a job), `client` 103/103, and `vite build` clean. No live order was placed and no MetaAPI request left the test process.

# Delivery outcomes

- [x] **Secure MT4/MT5 account setup:** Users can create an account setup from the Trading Accounts page using an account name, MT4/MT5 platform, and broker server. Signal Desk creates the account through MetaAPI on the backend and presents a MetaAPI-hosted secure configuration link so the user enters trading login/password there, not into Signal Desk. - [x] **Backend rules engine:** Before placing an order, check Gate 1: the user's Auto-Trading toggle is ON and the runtime safety switch is available. Every `/api/admin/*` route re-checks the role from PostgreSQL on each request (401 when signed out, 403 for standard users). Admins cannot demote or suspend their own account.

## Phase 3: Paystack billing

- [x] **Unlink deletes the MetaAPI account:** `DELETE /api/metaapi/accounts/:accountId` now resolves the owned account, deletes it from MetaAPI (`DELETE /users/current/accounts/:id`) through the same cleanup helper used by full account deletion, then removes the local link and clears Auto-Trading/execution selection. Provider failures are logged and returned as `metaApiCleanup` but never block the unlink; accounts billed to a user's own MetaAPI token are skipped.
- [x] **Plans and prices:** Free, Pro (₦2,500/month), and Premium (₦6,000/month), configurable through `PAYSTACK_PLAN_*_AMOUNT`. The server always recalculates the amount, so a tampered browser payload cannot change the charge.
- [x] **Hosted checkout:** `POST /api/billing/checkout` creates a `pending` `billing_transactions` row with a server-generated reference and returns Paystack's `authorization_url`; the browser never sees the secret key and card data stays on Paystack.
- [x] **Verification and webhooks:** the `/billing/callback` page calls `GET /api/billing/verify`, which re-verifies with Paystack. `POST /api/billing/webhook` validates `x-paystack-signature` (HMAC SHA512 over the raw body, constant-time compare), handles `charge.success` only, ignores unknown references, and returns 401 for a bad signature.
- [x] **Idempotent fulfilment:** one shared routine marks the transaction `success` once, rejects amount/currency mismatches, updates `users.subscription_*` and `plan_limits`, and increments a promo code only on the first success. Replayed webhooks and duplicate callback verifications are no-ops.
- [x] **Promo codes at checkout:** percentage/fixed discounts, expiry, usage caps, and a minimum-charge guard, applied server-side with the existing admin-created code table.
- [x] **Plan limits:** trading accounts and Telegram channels are gated by the effective plan (`402` with `upgradeRequired`), falling back to Free limits as soon as a subscription is not active.
- [x] **Cancel, resume, and expiry:** cancel keeps access until the period ends, resume clears it, and an hourly sweep downgrades lapsed subscriptions to Free.
- [x] **Billing UI:** a Billing page (current plan, limits, plan cards, promo code, payment history), a `/billing/callback` status page, and an admin Billing panel with active subscriptions, gross collected, discounts, and recent transactions.

**Billing validation:** backend suite passes 77/77. The end-to-end harness (in-memory PostgreSQL + mocked Paystack and MetaAPI transports) passes 24/24 checks, including unlink deletion and failure handling, free-plan limits, checkout pricing, tampered amounts, signed webhook fulfilment and replay, bad signatures, verify-path amount mismatch, promo discounts with single-use accounting, cancel/resume, and the expiry sweep. Billing UI checks pass 13/13 and the admin UI checks pass 18/18. No live Paystack charge was made.

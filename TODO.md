## Break-even stop management

- [x] **Narrow-only stop moves:** once the market has travelled `breakEvenTriggerPoints` in favour of a trade Signal Desk opened, its stop is moved to entry plus `breakEvenOffsetPoints`. Distances are MetaTrader points aligned onto the symbol `tickSize` (a buy rounds down, a sell rounds up); a stop is never widened and a position already at least as protected is marked handled.
- [x] **Broker rules respected:** `stopsLevel` and `freezeLevel` are checked before any request, so a stop that is too close to the market is deferred and retried instead of rejected; the decision always uses a fresh synchronized quote and the live position from the terminal state, and fails closed on crossed or missing prices, a missing specification, or an unrecognized position direction.
- [x] **Persisted per position:** `break_even_moves` keeps one row per broker position (status `moved`, `already_beyond`, `closed`, `deferred`, `failed`, `unknown`, the previous and new stop, the quote used, attempt count, next retry, and the sanitized provider message). Terminal statuses are never retried; a deferral retries without consuming an attempt while a broker rejection retries up to ten times; `unknown` never retries because the broker may already have applied the change. `TRADE_RETCODE_NO_CHANGES` counts as protected, and the recorded `trades.stop_loss` follows the broker.
- [x] **Same loop, never in the way:** the sweep runs in the execution worker after an idle tick, and every fifth iteration while orders are being processed so a busy signal stream cannot starve protection, throttled by `BREAK_EVEN_SWEEP_INTERVAL_MS` (default 5000 ms, floor 1000). Auto-Trading off, an account change, an undeployed account, or the runtime switch all stop the request before it reaches MetaAPI; only outcomes the broker actually answered consume an attempt; changing a distance re-arms handled positions.
- [x] **MetaAPI surface widened once:** the trading adapter now calls the SDK's `modifyPosition(positionId, stopLoss)` only (no take profit is ever sent, so the existing take profit survives) and keeps the provisioning/user token server-side. No close, partial close, or pending-order capability was added.
- [x] **Settings and UI:** `GET/PUT /api/settings` carries `breakEvenEnabled`, `breakEvenTriggerPoints`, and `breakEvenOffsetPoints` with server-side bounds; Risk settings gains a Break Even section that states the scope and that Auto-Trading off also stops these moves, and each trade row shows its break-even outcome and reason. The required live-trading warning text is unchanged.

**Break-even validation:** backend suite passes 150/150, with 27 new tests for the decision function (trigger, both sides, tick alignment, never-widen, stops/freeze deferral, fail-closed inputs), failure classification (deferred vs rejected vs ambiguous), and the sweep (runtime gate, throttle, re-check before the write, closed positions, `NO_CHANGES`, provider rejection sanitized without the token, unsynchronized account, worker ordering, and a failing sweep not taking the loop down). ## True trailing stop on top of break even

- [x] **One sweep, one rulebook:** the trailing stop is not a second job. `sweepBreakEven()` now computes both targets — entry + offset for break even, and market − distance for the trail — and takes whichever is **more protective**, so turning trailing on can never weaken break even and vice versa. Settings are `trailing_stop_enabled` and `trailing_stop_distance_points` (default 10 points, validated 1-100000 server-side, never clamped).
- [x] **The three guarantees held:** a stop only ever moves tighter, so a retracing market yields `wait` rather than a loosening write (and `already_beyond` becomes a `wait` while a trail is running, because a trail is a standing instruction, not a one-off job); every decision reads the price, the position's live stop, and the symbol specification from a single synchronized account read, with `waitForFreshPrice` refusing a stale quote; and `unknown` from `classifyBreakEvenFailure` still means no scheduled retry — `unknown` and `closed` rows are never re-offered to the sweep, so an unconfirmed move can never be resent.
- [x] **Ledger that survives repetition:** `break_even_moves` keeps exactly one row per broker position and adds `move_count` and `trailing_distance_points`; the write guard that made a terminal row untouchable now admits a `ratchet` write only for a workspace with trailing on, so break even's one-write-per-position behaviour is byte-for-byte unchanged while a trail can keep updating its own row. Candidate selection re-includes `moved`/`already_beyond` rows only when trailing is enabled and no new query parameter was needed, keeping the throttles (`BREAK_EVEN_SWEEP_INTERVAL_MS`, sweep limit, `stopsLevel`/`freezeLevel` backoff, ten-attempt cap) in force for both.

## Admin platform controls: health, kill switch, support access, audit trail

- [x] **A kill switch that can actually be flipped at runtime:** `AUTO_TRADING_RUNTIME_ENABLED` is read once at boot, so it can stop execution but nobody can change it during an incident. The switch now lives in `admin_settings` (`auto_trading_kill_switch`) and `processJob()` asks it - through the injected `isTradingPaused` dependency - once before any work on a job and again immediately before the trade row is written and the order is sent, so engaging it stops new trades for every workspace on the next claim with no restart and no half-submitted order. Paused jobs are skipped with the reason recorded, an unreadable switch is treated as paused rather than as permission, and `sweepBreakEven()` deliberately does not consult it: taking a stop away from an open position mid-incident is the opposite of a pause. Covered by 5 tests in `server/test/execution-pipeline.test.js`, one of which asserts `createMarketOrder` is never reached and another that the switch is asked exactly twice per executed job.
- [x] **System health read from the records that already exist:** `server/services/system-health.js` unions `trades` (`rejected`/`unknown` with an error), `execution_jobs` (`failed`/`unknown`, minus any job whose trade already carries the failure), `break_even_moves` (`failed`/`unknown`), and `signals.parse_error`, over one `hours` window shared by the list and the per-kind counts, plus queue depth, overdue-while-queued, last claim, and orders filled. No parallel error table, so nothing can drift and pre-existing incidents are visible on day one. `checks` carry the label, headline, and sentence the panel prints - wording produced server-side so a UI cannot invent a reassuring line - and a section that failed to read returns `unknown`, never `ok`, with `errorsAvailable` separating "nothing wrong" from "could not look".
- [x] **Support access without touching the password:** `POST /api/admin/users/:id/impersonate` mints a separate 1-hour JWT (`purpose: 'impersonation'`, `sub` = customer, `act` = admin) whose random session id is stored only as a SHA-256 hash in `support_sessions`. `authenticate` then enforces the promise: the row must still be live and unrevoked on every request, any non-`GET` is refused with 403 except closing the session itself, and `requireAdmin` rejects support tokens outright - so an admin impersonating another admin gains nothing. Self-impersonation and suspended targets are refused with reasons. `client/src/lib/support-session.js` keeps the token in `sessionStorage` (dies with the tab), drops expired or unreadable records instead of trusting them, and the app swaps `authToken` so the whole dashboard renders as that user while the admin's own token is retained for closing the session from the banner.
- [x] **Manual adjustments that respect both halves of billing:** `PATCH /api/admin/users/:id/subscription` grants a plan, adds 1-365 days, or sets an exact expiry, always with a reason. `users` (plan, status, `plan_limits` snapshot) and `subscriptions` (`plan_key`, `status`, `current_period_end`) are written in one transaction, the user mirror is always re-derived from the subscription row rather than guessed twice, an extension counts from the later of now and the current end so it can never shorten a paid period, and a canceled row revives as `non_renewing` with `cancel_at_period_end` so support can give time without silently re-subscribing anybody at the gateway. Paystack is never touched, and the response says so - again, with the plan code, when a gateway subscription is attached. Fixing this surfaced a latent schema bug: `subscriptions_plan_check` still listed only `free/pro/premium` after Starter became purchasable, which would have rejected the row a verified Starter payment writes; the constraint is now re-created idempotently including `starter`.
- [x] **An append-only audit trail with the admin's email in it:** `admin_audit_logs` plus `server/services/audit.js`. Price changes, promo-code writes, suspensions and role changes, subscription adjustments, kill-switch moves, announcements, and support sessions all append one entry holding the action key, a plain-language summary, the target, scrubbed metadata, and the timestamp - with `actor_email` denormalised so a later rename or deletion cannot rewrite history. Metadata keys matching token/password/secret/credential patterns are dropped and matching values redacted (promo codes survive, they are business data); entries are capped so one payload cannot bloat the table. A write failure is logged as an error but never turns a successful admin action into a 500, and there is no update or delete path anywhere in the app. `GET /api/admin/audit-logs` pages and filters it; the panel's Audit log tab searches by admin email or wording.
- [x] **Global announcements with per-user dismissal:** `announcements` (message 4-500 chars, `info`/`warning`/`critical`, optional start/end window, active flag) with `announcement_dismissals` keyed by `(user_id, announcement_id)`, so dismissing on a phone keeps it dismissed on the web without hiding it from anyone else. `GET /api/announcements/active` returns up to three live, undismissed banners - critical first - and the dashboard renders them above the workspace with a Dismiss action; `client/src/lib/platform-view.js` owns the wording, severity fallback, and the `role`/`aria-live` pair, and a banner that could not be read renders nothing rather than guessing. Retiring is a soft close that keeps the row, its dismissal counts, and the audit trail; the PATCH route turns a window CHECK violation into a readable 400 instead of a 500.
- [x] **UI work kept to the standard the rest of the admin panel follows:** `AdminPanel` gained System health, Announcements, and Audit log sections (tab bar now six deep), the user table gained Impersonate and Adjust plan affordances with their forms in a row expansion that first states the account's current plan, status, period end, and whether a gateway subscription is attached, and the kill switch card shows the state read back from the server after a toggle instead of the button that was pressed. `ExecutionSettings` gained `platformPause`, fed by the existing `GET /api/settings` payload, so a user whose own toggle is on is told the platform paused it - with the reason - rather than being left to find a switch that is already correct.
- [x] **Guards against the specific ways this could have gone wrong:** `client/test/platform-admin-ui.test.mjs` asserts the kill-switch view never labels an absent read as `Live`, that an unreadable check is not `ok`, that a support token is never written to `localStorage` and never reaches `AdminPanel`'s own calls, that no component keeps its own kill-switch label map, and that the support bar contains no input, select, or textarea. The support-session tests assert the raw session id never appears in a stored parameter, that a revoked or expired row cannot redeem, that one admin cannot close another admin's session, and that `hours: 24` still yields 60 minutes.

Every new SQL string - including the full `db.js` migration with the new tables, indexes, RLS, and the replaced `subscriptions_plan_check` - was parsed with `pglast` 8.7. No live database or MetaAPI call was involved: reads and writes are asserted against fake pools, so the row-level behaviour of the new tables has not yet been exercised against PostgreSQL.

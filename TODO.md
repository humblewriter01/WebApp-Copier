# Delivery outcomes

- [x] **Secure MT4/MT5 account setup:** Users can create an account setup from the Trading Accounts page using an account name, MT4/MT5 platform, and broker server. Signal Desk creates the account through MetaAPI on the backend and presents a MetaAPI-hosted secure configuration link so the user enters trading login/password there, not into Signal Desk. Signal Desk never stores or logs the broker password. Users can refresh account status and request a new setup link. Account ownership is scoped to the signed-in user. Removing an account from Signal Desk does not delete it from MetaAPI. Provisioning an account does not itself place a trade; order execution remains controlled by the separately default-off Auto-Trading settings.
- [x] **Telegram chat search:** Add a search box directly above “Available groups & channels.” Filter chat names immediately while the user types, with a helpful no-match state.
- [x] **Telegram page copy:** Remove the MVP reference from the footer and replace it with a concise user-facing disclaimer. Replace the Render/free-tier warning under monitored chats with a simple message that monitoring may pause if the service goes to sleep.
- [x] **App-wide user-facing copy:** Remove developer/internal language, including references to Render, GitHub, environment variables, backend systems, database errors, system logs, and code jargon. Unexpected failures display understandable user-facing messages; useful validation and Telegram authentication errors remain specific and safe.
- [x] **Render auto-deployment:** Configure the existing API and static-site services to auto-deploy commits from `main` using the Render Blueprint's current commit-trigger setting. Preserve existing service names, build commands, environment, region, URLs, and deployment behavior otherwise.
- [x] **MetaAPI error and funding diagnostics:** When the MetaAPI API or SDK returns an error, capture its exact message, HTTP status, and safe error code. Check provider responses for deposit, billing/payment, insufficient-funds, or insufficient-balance errors and return the specific sanitized message to the frontend. If the connection fails before MetaAPI returns an HTTP response, surface the safe underlying network cause/code and say no provider response was received rather than claiming a deposit problem. Remove invisible Unicode formatting marks from the saved `auth-token` before using it as an HTTP header; reject any remaining unsupported characters with a safe, actionable message before making the request. The frontend displays the backend diagnostic instead of the generic connection fallback. Never expose tokens, broker passwords, stack traces, or unfiltered provider payloads. Keep unexpected internal errors generic.
- [x] **MetaAPI request contract and connectivity:** Use MetaAPI's documented provisioning hostname, pass the provisioning token in the `auth-token` header, and send the documented account payload (`name`, `server`, `platform`, `magic: 0`) without asking for or transmitting broker login/password. Generate the secure setup link with the documented configuration-link endpoint.
- [x] **Consistent navigation and page labels:** Audit all frontend navigation and page headers. Make the sidebar label and main page title match exactly for each section. Use **Account Notes** for reference-only labels and **Trading Accounts** for MetaAPI-connected accounts, updating related metric/heading/cross-link terminology so the two account areas are clearly distinguished. Use one shared navigation-label source for the sidebar and page title.
- [x] **Rate-limit proxy handling:** Configure the API to trust the Render reverse-proxy hop so rate limiting uses the originating client IP and no longer logs the unexpected `X-Forwarded-For` warning; do not trust all proxy hops.
- [x] **Execution Settings UI:** In Risk Settings, add an “Execution Settings” section and an “Enable Auto-Trading” toggle that is OFF by default. Add a “Lot Size Mode” dropdown with “Fixed Lot” and “Risk-Based (Calculated from Stop Loss)”. If Fixed Lot is selected, show “Fixed Lot Size” (example 0.01); if Risk-Based is selected, use the existing “Risk percent per position” field. Add “Maximum Open Trades” (example 3) and “Maximum Daily Trades” (example 10). Add a prominent red banner with exactly this text: “Warning: Enabling Auto-Trading will execute live trades on your connected broker account. Ensure you are using a demo account for testing. You are fully responsible for any financial losses.” Require an owned connected trading account to be selected. Replace the obsolete copy that says risk preferences never place trades.
- [x] **Telegram parsing and durable pipeline:** When a new monitored Telegram message is parsed and saved, retain the raw message and extracted symbol, BUY/SELL direction, entry price when present, stop loss, and take profit. Queue only new, deduplicated, safely parsed messages for users who have opted in. Do not execute manual notes or unclear messages. Persist jobs so process restarts do not lose state, but expire stale signals rather than executing them late.
- [x] **Backend rules engine:** Before placing an order, check Gate 1: the user's Auto-Trading toggle is ON and the runtime safety switch is available. Check Gate 2: use MetaAPI to fetch the selected account's live state and stop if the account has reached “Maximum Open Trades” or “Maximum Daily Trades”. Check Gate 3: stop if the account has reached the original “Daily loss limit (%)”. For Fixed Lot, use the configured fixed lot size. For Risk-Based, calculate volume from the live account balance and the signal's Stop Loss, using the broker's symbol tick value, tick size, minimum, maximum, and volume step. If required state or a daily-loss baseline is unavailable, fail closed.
- [x] **MetaAPI order placement and result logging:** Add a backend execution service that submits the calculated symbol, BUY/SELL type, volume, stop loss, and take profit through the MetaAPI JavaScript trading SDK after the account connection is synchronized. Handle successful responses and provider rejections. Create/update a `trades` row with order status, broker order/position identifiers, and sanitized API response/error. Do not add a simulation or paper-trading path, and do not automatically retry an ambiguous order response that could duplicate a trade.
- [ ] **Safe execution runtime:** Keep each user's Auto-Trading toggle OFF by default; the user explicitly requests that the backend execution worker run continuously whenever the API service is awake. Set the API-only `AUTO_TRADING_RUNTIME_ENABLED` switch to `true`, but never place orders unless a user opts in and selects an owned, deployed connected account while the mandatory red warning remains visible. The API and static website are separate Render services, so UptimeRobot must monitor the API `/health` endpoint rather than the website. Explain that a keep-alive monitor does not guarantee uninterrupted service, expire stale work, and fail closed when safety data is missing. Keep MetaAPI trading credentials server-side and do not change or upgrade the Render plan.

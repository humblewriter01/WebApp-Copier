## Break-even stop management

- [x] **Narrow-only stop moves:** once the market has travelled `breakEvenTriggerPoints` in favour of a trade Signal Desk opened, its stop is moved to entry plus `breakEvenOffsetPoints`. Distances are MetaTrader points aligned onto the symbol `tickSize` (a buy rounds down, a sell rounds up); a stop is never widened and a position already at least as protected is marked handled.
- [x] **Broker rules respected:** `stopsLevel` and `freezeLevel` are checked before any request, so a stop that is too close to the market is deferred and retried instead of rejected; the decision always uses a fresh synchronized quote and the live position from the terminal state, and fails closed on crossed or missing prices, a missing specification, or an unrecognized position direction.
- [x] **Persisted per position:** `break_even_moves` keeps one row per broker position (status `moved`, `already_beyond`, `closed`, `deferred`, `failed`, `unknown`, the previous and new stop, the quote used, attempt count, next retry, and the sanitized provider message). Terminal statuses are never retried; a deferral retries without consuming an attempt while a broker rejection retries up to ten times; `unknown` never retries because the broker may already have applied the change. `TRADE_RETCODE_NO_CHANGES` counts as protected, and the recorded `trades.stop_loss` follows the broker.
- [x] **Same loop, never in the way:** the sweep runs in the execution worker after an idle tick, and every fifth iteration while orders are being processed so a busy signal stream cannot starve protection, throttled by `BREAK_EVEN_SWEEP_INTERVAL_MS` (default 5000 ms, floor 1000). Auto-Trading off, an account change, an undeployed account, or the runtime switch all stop the request before it reaches MetaAPI; only outcomes the broker actually answered consume an attempt; changing a distance re-arms handled positions.
- [x] **MetaAPI surface widened once:** the trading adapter now calls the SDK's `modifyPosition(positionId, stopLoss)` only (no take profit is ever sent, so the existing take profit survives) and keeps the provisioning/user token server-side. No close, partial close, or pending-order capability was added.
- [x] **Settings and UI:** `GET/PUT /api/settings` carries `breakEvenEnabled`, `breakEvenTriggerPoints`, and `breakEvenOffsetPoints` with server-side bounds; Risk settings gains a Break Even section that states the scope and that Auto-Trading off also stops these moves, and each trade row shows its break-even outcome and reason. The required live-trading warning text is unchanged.

**Break-even validation:** backend suite passes 150/150, with 27 new tests for the decision function (trigger, both sides, tick alignment, never-widen, stops/freeze deferral, fail-closed inputs), failure classification (deferred vs rejected vs ambiguous), and the sweep (runtime gate, throttle, re-check before the write, closed positions, `NO_CHANGES`, provider rejection sanitized without the token, unsynchronized account, worker ordering, and a failing sweep not taking the loop down). ## True trailing stop on top of break even

- [x] **One sweep, one rulebook:** the trailing stop is not a second job. `sweepBreakEven()` now computes both targets — entry + offset for break even, and market − distance for the trail — and takes whichever is **more protective**, so turning trailing on can never weaken break even and vice versa. Settings are `trailing_stop_enabled` and `trailing_stop_distance_points` (default 10 points, validated 1-100000 server-side, never clamped).
- [x] **The three guarantees held:** a stop only ever moves tighter, so a retracing market yields `wait` rather than a loosening write (and `already_beyond` becomes a `wait` while a trail is running, because a trail is a standing instruction, not a one-off job); every decision reads the price, the position's live stop, and the symbol specification from a single synchronized account read, with `waitForFreshPrice` refusing a stale quote; and `unknown` from `classifyBreakEvenFailure` still means no scheduled retry — `unknown` and `closed` rows are never re-offered to the sweep, so an unconfirmed move can never be resent.
- [x] **Ledger that survives repetition:** `break_even_moves` keeps exactly one row per broker position and adds `move_count` and `trailing_distance_points`; the write guard that made a terminal row untouchable now admits a `ratchet` write only for a workspace with trailing on, so break even's one-write-per-position behaviour is byte-for-byte unchanged while a trail can keep updating its own row. ## What a captured message means, and how it can be removed

- [x] **Suspend now says what the backend said - and so does the backend.** The refusal sentences from `PATCH /api/admin/users/:id` reach the panel unchanged, and a refused account edit is no longer invisible: the server logs `Admin account edit refused` with the actor, the target, the status, and the field *names* that arrived, and a refused suspension writes `user.suspension.refused` to `admin_audit_logs`. A successful one logs which columns actually changed. The class of bug this closes was the silent one - a form that looked busy and did nothing, with no request and no log line to find later.
- [x] **The GramJS listener stopped being silent, which is how the drop was found.** Monitoring compared `channels.channel_id` with one string derived from one accessor (`message.chatId`), so whenever Telegram handed the other spelling of the same channel (`-100…` against the bare id) every message failed to match and was returned unhandled, with no row, no error, and nothing in the log while manual entry kept working. `server/services/telegram-peer.js` now owns that boundary: `resolveTelegramChatId` tries the message, its `peerId`/`chatPeer`, the event's `update`/`chatPeer`, `toPeer()`, `toObject()`, and Long-style stringification before concluding nothing; `telegramPeerIdVariants` produces every spelling a row could hold and the lookup matches with `channel_id = ANY($2::text[])`. Basic-group ids are matched, never rewritten, because canonicalising `-7` to `-1007` invents a chat. `telegramMessageText` reads text or a media caption, strips the zero-width marks Telegram scatters through channel posts, and caps the payload at 4000 characters - invisible padding was also breaking the header regexes. **Every** update is then logged with its outcome (`captured`, `ignored: that chat is not monitored`, `carried no text to read`, `had no chat id to match on`), the parse/save is wrapped so a storage failure is logged instead of swallowed, and unparsed or refused messages are stored anyway because a capture is not a reward for parsing cleanly. `GET /api/telegram/status` reports `listening`, `messagesSeen`, `signalsSaved`, `lastMessageAt`, `lastChatId`, `lastError`, and `monitoredChannels`, and re-attaches a missing handler when it finds a connected client with none - the failure mode itself, made visible and self-repairing.
- [x] **An unread signal explains which part it is missing.** `parseSignal` returns the same seven fields plus `directionInferred`, `hasTradingData`, `missing: {entryPrice, stopLoss, takeProfit}` and a `blockers` array (one code and one sentence each), and `parseError` is the first blocker's message, so every sentence the app has always written is still exactly the same text. A direction is inferred only when the message states none at all, an entry and exactly one target exist, and the two differ - and the inference immediately adds its own blocker, so an inferred direction can be read but never traded. `SELL XAU/USD` with a stop and no target was executable before and still is: a target is for reading, never an eligibility rule, and that asymmetry is now a test. The panel shows **Inferred**, **Missing SL**, and **Missing TP** badges, and "No clear signal" is reserved for a message that said nothing about a trade - a legible note missing one price reads "Needs review" with the server's sentence under it.
- [x] **Advanced Safety: a workspace can now decide whether a stop-less signal may execute.** `settings.block_execution_without_stop_loss` (boolean, `DEFAULT TRUE`, added by the app's own idempotent startup migration) is read by `GET /api/settings`, written by `PUT /api/settings` where an absent value means on, read at capture time to decide `execution_ready`, and read by the engine at claim time. Risk settings were regrouped into **Core Risk**, **Trade Management**, and a closed **Advanced Safety** disclosure whose summary says `Blocking`/`Allowed` before it is opened. Off permits an SL-less signal only in **Fixed Lot** mode - risk-based sizing divides by the distance to a stop that would not exist, and those signals are refused with that reason. Fixing the gate also exposed an older defect: the claim query read `Number(item.stop_loss)`, and `Number(null)` is `0`, which is finite and on the correct side of any price - so a signal with no stop was never actually blocked there, it was sent to the broker and stored as a stop at **0**. - [x] **Signal history is deletable, and trades are not.** `DELETE /api/signals/:id`, `DELETE /api/signals`, `DELETE /api/admin/signals/:id`, `DELETE /api/admin/users/:id/signals`, `GET /api/admin/signals/purge-preview` and `POST /api/admin/signals/purge` (default 30 days) all run one statement *pair* in a single transaction borrowed from the pool: `UPDATE trades SET signal_id=NULL …` then `DELETE FROM signals … RETURNING id`. ## A trade is never naked because the provider forgot

- [x] **Fallback Safety Nets: the workspace can supply the leg a signal omitted, in points.** `settings.fallback_stop_loss_points` and `settings.fallback_take_profit_points` (`NUMERIC`, nullable — no row value means no net) are added by the app's own idempotent startup migration, read by `GET /api/settings`, written by `PUT /api/settings` through `readFallbackPoints` (a whole number in `1…1000000` or blank, anything else answered by one sentence naming the field, never clamped), read at capture time to decide `execution_ready`, and read by the engine in the same query that claims the job. The order is fixed: the signal's own value, then the fallback, then the block — so a level the channel stated is never overwritten, and a trade completed by a net is not an override and never logged as one.
- [x] **A fallback is priced against a live quote, not against the signal's stale entry.** `applySafetyNets` computes `order price ∓ points × tickSize` and aligns onto the broker's tick grid *away* from the market (down for a buy's stop, up for its target, mirrored for a sell), so a rounding step can neither tighten risk nor land inside `stopsLevel`. A stop is judged against the price the position is valued at and a target against the price it has to beat, because reusing one rule for both made a correct 4000-point target look unusable. `signals.execution_note` then says the level came from the workspace — with `above`/`below` written for the side actually traded — and an executed job is allowed to leave that explanation behind it, which is why `updateJob` gained a note argument rather than a special case.
- [x] **`Block execution if Take Profit is missing` is the other half of the guard, and it is on by default.** `settings.block_execution_without_take_profit` (`BOOLEAN NOT NULL DEFAULT TRUE`) refuses a signal with no target — a position with nothing planned to close it used to be the one thing this app would happily open. It is independent of the stop block, and the folded summary reads `Blocking` while either stands. An override is only reachable with the block off *and* no fallback, and says so: `Trade executed without Take Profit (User Override).` on the log line, with the user, job, signal, symbol and account in the same JSON record, and on the signal row.
- [x] **A net that cannot be honoured is reported, not dropped.** No tick size for the symbol, a distance inside the broker's `stopsLevel`, a result at or below zero, or a leg too small to clear the spread each produce `*-net-unusable`, and the block then applies to that leg as if no fallback existed — with both facts in the one sentence the user reads ("…the broker requires stops at least 50 points from the market, and the fallback distance is 10"). Quietly ignoring a setting somebody configured is how a "safe" workspace ends up trading without the stop it believes it asked for.
- [x] **One policy, two questions, and the `Number(null) === 0` trap closed for good.** `server/services/signal-safety.js` holds `captureSafety` ("may this message be queued at all?") and `applySafetyNets` ("what prices go on this order?"), and `index.js` and the engine both ask it instead of restating the rule; `isBlockedOnlyByStopLoss` and the capture-side `allowMissingStopLoss` expression are gone, because two copies of a safety rule is how a signal got stored as executable and then refused, or stored as refused and then traded. Absence is tested with `statesPrice` before any conversion, so `null`, `undefined` and `''` are all "the leg does not exist" and none of them is 0.
- [x] **Risk settings copy extended, not rewritten.** The three controls are in the same folded **Advanced Safety** group under the existing sentences: two block toggles, then `Fallback Stop Loss (points)` and `Fallback Take Profit (points)` (blank field, `None` placeholder, help text saying the channel's own value always wins and that an unusable distance is reported rather than ignored). The two lines that the new toggle made untrue were corrected — the badge titles for **Missing SL** / **Missing TP** no longer promise that a missing target can never stop an order, and one bullet now says the block, not the parser, decides.

## An order is not sent into a market, a broker, or a duplicate

- [x] **A price has to be current, not merely present.** `guardQuote` in the new `server/services/execution-defense.js` refuses a market order against a quote older than 2 seconds, against one dated in the future past the same window (clock skew must not be able to look like permanent freshness), against one with no timestamp at all, and while the account's own `link` says `connectedToBroker` or `synchronized` is false. - [x] **The three caps the workspace sets for itself are one decision now.** `guardExposure` compares the live terminal state against `max_open_positions` (positions *and* resting orders), the day's drawdown against the UTC-day equity baseline versus `daily_loss_limit`, and `max_daily_trades` against the greater of the broker's deal count and the local rows - all inclusive, all before MetaAPI is touched, each with its own sentence (`Execution skipped: Max open positions reached.`, `… Daily loss limit reached.`, `… Maximum daily trades reached.`). Transient and provably never delivered (`-10`, `-5`, `-6`, a requote, `MARKET_CLOSED`, `TOO_MANY_REQUESTS`) re-queues the job with `execution_jobs.next_attempt_at` set from an exponential wait (`1.5s`, `3s`, `6s`, capped, three attempts in total) that the worker's claim honours, so a restart cannot lose the backoff or start early; the signal's own two-minute window still wins, and a job with no room left expires instead of pretending. `unknown` delivery (`-11`, `-7`, `10012`, a socket that hung up mid-request) is never retried, whatever the message says, and the trade row is left at `submitting` during a wait so that a retry continues on the row it belongs to instead of describing itself wrongly.

## A deploy that bound no port, and the three rules that make it impossible to hide

- [x] **The port opens first.** `await initializeDatabase()` used to sit in front of `httpServer.listen`, so a database that was merely slow became a service that answered nothing on any port, and Render's only complaint was `Port scan timeout reached, no open ports detected`. Startup now binds, then migrates behind the open port, then starts the runtime.
- [x] **The schema is one statement at a time.** The whole schema was one string sent as one query, i.e. one implicit transaction holding every `ALTER TABLE`'s lock until the last statement committed - and any reader of those tables (the worker, a dashboard query, the previous instance still serving traffic) parks it forever. `services/schema-sql.js` splits it, respecting `DO $$ ... $$`, string literals, and comments; `db.js` is otherwise untouched, including the template literal and its backtick rule.
- [x] **A blocked statement gives up and says so.** `lock_timeout` (5 s), `statement_timeout` (120 s), three tries, then an error that names the statement: `Schema statement 87 of 134 never got the lock it needed after 3 attempts: ALTER TABLE ... - canceling statement due to lock timeout`. The connection checkout has its own deadline because a host that accepts a socket and then never replies is invisible to a TCP timeout.
- [x] **A failed migration no longer exits the process.** It retries with a capped backoff and heals itself; only a missing `DATABASE_URL` or `JWT_SECRET` still fails fast. ## Flutterwave billing in two currencies

- [x] **Prices became a table, and grew a second column.** `plans` (`plan_key`, `interval`, `price_ngn_minor`, `price_usd_minor`, `price_history`, `updated_by`) is the source of truth for what a tier costs, with `plan_provider_sync` keyed on **(plan, currency)** holding the Flutterwave payment plan id, sync status, confirmed amount and last error. `plan_limits` stayed what it always was — the per-user allowance snapshot on `users` — because a table of one row per user cannot also be a price list. Prices already kept in `admin_settings` are copied across once at boot, naira only; the legacy `paystack_plan_*` mirror is deliberately not carried, because a `PLN_…` code is not something Flutterwave can honour.
- [x] **Admin Panel → Pricing & Plans sets both currencies.** Two fields per plan, each with its own currency symbol and placeholder (dollars shown in dollars, not in hundredths), a per-currency "use the deployed default" button, two sync states and two "Sync now" buttons, and a warning when a currency is priced on its own: an asymmetric catalogue is almost always a mistake, and the two prices are two separate provider objects that a trader can pay either of. `PUT /api/admin/pricing` accepts `amount` / `usdAmount` (or their `*Minor` forms), `null` clears a currency back to the deployed default, and a save re-syncs only the currencies whose amount actually moved. `GET /api/admin/billing` reports revenue per currency and never a combined total, because ₦ and $ added together describe neither.
- [x] **`POST /api/billing/checkout` takes a `currency` and prices in it.** `{ plan, promoCode, currency }` → the currency is checked against `SUPPORTED_CURRENCIES`, the price for it is read from the `plans` row, the promo discount is applied **after** the currency is known (a fixed allowance is expressed in the currency being paid), and `billing_transactions` stores hundredths as always. The browser still cannot change a number: it picks a column, never an amount.
- [x] **The unit is converted exactly once, at the provider boundary.** Flutterwave is fed the major unit — 60000 for a ₦60,000 plan, 39 for $39 — while every stored figure in this repository is hundredths. `toMajorAmount` divides, `amountString` renders that value as a fixed-point string (never exponential, because `1e+21` would be truncated to a fraction by the provider), and the checksum is computed over the **same string that is sent** rather than over a re-derived copy. The `payload_hash` is sha256 over `amount + currency + customer email + tx_ref + sha256(secret key)`, which is what makes a field edited in transit a refused payment instead of a cheaper one. `server/test/billing-multi-currency.test.js` asserts the outgoing request body: `amount` is the string `'60000'`, `'105000'`, `'150000'`, `'39'`, `'69'`, `'99'`, a re-priced Pro row becomes `'89000'` / `'45'`, and a 25% promo yields `'78750'` / `'51.75'` with `discount_minor` 1725 — while the stored `amount_minor` stays ×100 of what went out.
- [x] **A unique `tx_ref` per attempt.** `sdb_<user id>_<unix seconds>_<random 4 bytes>`, minted only when a new checkout is actually started, so an in-flight price change cannot strand a payment that was opened against the old price: the same request re-presents the same link and the same amount (`payloadHash` decides whether the quote has moved).
- [x] **`POST /api/billing/webhook` is a static header check, not a signature.** `verifyWebhookHash` compares the `verif-hash` header with `FLW_WEBHOOK_HASH` in constant time; a mismatch, a missing header, and a non-replayable body are 401s, and an unset `FLW_WEBHOOK_HASH` is a 503 that refuses every event rather than a webhook that accepts everything. `charge.completed` then asks Flutterwave `GET /v3/transactions/verify_by_reference?tx_ref=…` and grants nothing until `status === 'successful'`, `currency` matches the stored row, **and** the major-unit amount equals the stored hundredths ÷ 100. An underpayment is `409 AMOUNT_MISMATCH`, a wrong-currency payment is `409 CURRENCY_MISMATCH` (a $39 payment cannot buy a ₦60,000 plan), and an overpayment grants the plan and logs `overpaymentMinor` for a human to refund. The endpoint always answers 200 once the event has been read, because a 3xx or 5xx makes Flutterwave retry for an hour.
- [x] **Renewals per currency.** `subscribe.*` events key idempotency on `sdb_flwsub_<subscription id>_<cycle start yyyymmdd>` — a renewal arrives with no reference this server minted — and are matched to an account by the customer email Flutterwave holds, since a Flutterwave subscription is bound to an email and cannot be moved. An event that cannot be tied to exactly one account is dropped, never guessed. `planChargeDecision` is per (plan, currency), so a naira mirror that is confirmed and a dollar mirror that is stale renews in naira and takes a one-time dollar payment; `PUT /v3/payment-plans/:id` re-prices existing subscribers from their next cycle, and "leave my subscribers alone" creates a **new** plan id instead, so nobody is silently moved to a price they did not agree to.

- [x] **Provider vocabulary stays off the trader's screen.** No `tx_ref`, no kobo, no checksum, no plan id, no "minor units" in any customer-facing sentence — what a customer reads is the amount, the currency, and that Flutterwave processes the payment. ## The update state GramJS never had

- [x] **The deaf stream has a name, and now a repair.** A GramJS session can be connected, have its handler in the library's own `_eventBuilders`, and be pushed nothing forever: this version keeps no `pts` at all (`session.processUpdates` is commented out inside `_handleUpdate`, `catchUp()` is a `// TODO`, and each of the library's three `updates.GetState` calls throws the answer away), and a client that never reconciles is a client Telegram has no reason to keep writing to. `resyncUpdateState` in `server/services/telegram-listener.js` is the reconciliation: cached `pts` on the client (`UPDATE_STATE_KEY`, deliberately per-session so a rebuilt client starts clean), compared against the state the beat already asked for, and a gap the handler did not consume closed with `updates.GetDifference` sent with our own `pts`/`qts`/`date`.
- [x] **Asked from three places, and paid for by none of them when all is well.** The beat (it hands its `GetState` answer to the resync, so a healthy session issues exactly the request it was going to issue anyway), the handler attach (so a fresh session is never indistinguishable from a deaf one), and `restoreTelegramClient` - both the reconnect-in-place path and a new session after `checkAuthorization`. Identity is touched first via `getMe(true)`, which returns GramJS's cached self peer for free and, on the first beat after a rebuild, is the request that populates the field the dispatcher consults for every event builder.
- [x] **A recovery never pretends to be a push.** Messages returned by the difference are *not* dispatched through `_handleUpdate`: they flag `needsCatchUp`, and the catch-up stores them with its own dedupe, budget, and `replayed: true`. That is what keeps `replayed: false` meaningful as the thing an operator is testing for, and it is asserted, not assumed.
- [x] **The two escalations are different asks.** `updates.differenceTooLong` - Telegram saying the gap is beyond repair - is the one thing allowed to skip `STREAM_REBUILD_COOLDOWN_MS` (`update-state-too-far-behind`, `force: true`). A `pts` that stays static while the sweep keeps storing messages is the deaf signature: the difference is asked anyway (`force`, because the account claims there is nothing to send), and two beats of it escalate to `deaf-stream-pts-static` with `escalate: true` - a full new session, cooldown respected, so a skewed clock cannot turn the fix into a reconnect loop.
- [x] **`force` now means something on the server side.** `restoreTelegramClient` used to accept `force` and return the already-connected client unchanged, which made both the watchdog's rebuild and the Admin Panel's manual reconnect a no-op for exactly the sessions that needed them. `force`/`escalate` now step past that shortcut, disconnect the client being replaced, and reconcile the state before the session is handed back; only `force` skips the cooldown.
- [x] **The evidence is one line per session per beat.** `Telegram heartbeat beat` logs `pts`, `statePts`, `ptsDelta`, `gap`, `seen`, `catchUpSaved`, `replayFound`, `ms`, `listeningMs`; `heartbeatSummary` counts `resynced`, `recovered`, `deaf`, `gaps` (which reach `/health` as counts only - the per-session array is still destructured away before that payload is built); and the fleet summary carries `beatStatePts`, `beatGap`, `beatAction`, `beatDeaf` for the System Health tab.

- [x] **A slice is answered, and a refusal is told apart from a fault.** `updates.differenceSlice` is handled by a bounded loop (`DIFFERENCE_MAX_STEPS` requests, `DIFFERENCE_BUDGET_MS` of clock) that re-sends from the state each slice returned and adopts it every turn, so a budget that runs out mid-answer leaves the session further along and says `difference-partial`; a thrown `UPDATES_TOO_OLD`/`CHANNEL_DIFFERENCE_TOO_LONG` is classified into the same forced rebuild the result shape earns; a `FLOOD_WAIT_n` backs off only the difference requests, for exactly the seconds asked, with the state left *behind* on purpose so the next beat closes the same gap; and `AUTH_KEY_UNREGISTERED`/`SESSION_REVOKED` is the one answer that must not be retried at all.
- [x] **The recovery bound is the minute, not the stagger.** Every difference request - answered, empty, partial, or refused - flags `needsCatchUp`, which is what `rearmTelegramListeners` consumes every 60 seconds. A permanently deaf session is therefore a delay with a bound, and the no-data-loss rule is enforced by the code rather than by hoping the difference works.
- [x] **Three strikes and the session is ended, by the code.** An unreconciled beat is a strike; a second escalates to a new session; a third, on a session that has already been replaced inside `PTS_GAP_REAUTH_WINDOW_MS`, calls `onSessionUnrecoverable`, which sets `telegram_connected=FALSE` (leaving the session string for a last admin attempt), drops the in-memory entry, and publishes `reauthRequired` on the session status. One verdict per `STREAM_REBUILD_COOLDOWN_MS`, reset by any beat that reconciles and by any re-attach.

## The provider's keep-alive noise, counted instead of printed

- [x] **The provider's `Error: TIMEOUT` is counted at the client that produced it.** GramJS's `_updateLoop` races its own ping against a 10-second timer, prints the failure through `client._log`, and reconnects the sender - which on Render reads as hundreds of stack traces an hour for a transport the library is already fixing. `services/telegram-keepalive.js` recognises the error by its message *and* its throw site (never by "the stack mentions telegram", which would also match every failure inside our own dispatcher callback), suppresses exactly one print per recognised error through the logger's own `canSend` gate, and publishes the count per client per window plus on `/health`. No `console` patch, and everything else is printed as it was.
- [x] **The summary line is shaped like a rate, not a tally.** `count` is lifetime and `windowCount` is since the last summary, `pingCyclesPerWindow` is the library's own cadence as the yardstick (~33 per five-minute window), and `affectedClients`/`guardedClients`/`suppressedTotal` say whether one workspace's path is flappy or the fleet is having a data-center problem. A count that only ever climbs cannot answer "is it spiking", which is the one question the line exists for.
- [x] **A flap is not a fault, and the watchdog is told so.** `transportFlap` gives the beat the client's keep-alive record: one unanswered probe inside `KEEP_ALIVE_FLAP_GRACE_MS` is logged as `flapping` and deferred, the second consecutive one rebuilds as before, and keep-alive noise can never by itself mark a session `deaf`, raise a strike, or declare it unrecoverable. `connectionRetries` went 3 → 5 so the sender has at least as long to reconnect as it gives itself to time out; `timeout` is deliberately not passed, because this version stores it and never reads it.

## The server is checked against types without being rewritten in TypeScript

- [x] **`allowJs` + `checkJs` over all 41 sources (19,142 lines), `strict: false`, and nothing renamed.** `server/tsconfig.json` existed before this and had never been run; the first run answered with **372 errors**, and it is at **zero** now. The work was not annotating JavaScript for its own sake: 242 of those errors were `Property 'x' does not exist`, and almost every one of them was the same root cause - a destructured parameter with a default (`function createX({ pool, log = console } = {})`) is typed by TypeScript from its *defaults*, so members that had none do not exist and the ones that did exist are typed as their default value (`log = console` made the logger an uncallable object; `runtimeEnabled = () => false` made the return type the literal `false`, so `=== true` "had no overlap"). Replacing that inference with declarations is the whole change: **67 `@typedef {Object}` blocks and 321 `@property` lines**, each beside the function it describes, plus one global file.
- [x] **`server/types/app.d.ts` holds the four things a `.js` file cannot show an inference.** What a service may put on an `Error` (19 fields - `status`, `code`, `userMessage`, the four `metaApi*` ones, the two Telegram-session flags - each documented with the file that sets it, which is what the enforcement test checks in both directions); what the logging seam is (`ServiceLogger` level-first, `LoggerMethods` console-shaped, every method optional because `createAccountCleanup` genuinely receives a `warn`-only view); what a database handle accepts (`PoolLike`: `query(sql, params)` and nothing else, since that is all 234 call sites do); and the row shapes for `users`, `channels`, `signals`, `trades`, `settings`, `promo_codes`. The rows encode the fact that has caused more bugs here than anything else: **`pg` returns `NUMERIC` as a string**, so a price is `string | null` and `Number(row.entry_price)` is the code being correct rather than defensive - while `row.entry_price > 0` is now a compile error instead of a rule of thumb. Nothing in the file is folklore: two of its tests fail if a declared field is no longer set anywhere, or if a row type names a column `db.js` does not create.
- [x] **The checker found a shipped defect on its first day.** `onSessionUnrecoverable` - the rung that tells a workspace to sign in again after a session that cannot be reconciled - opened with `Number(userId)` and returned unless the result was a positive integer, but `users.id` is a UUID and the capture map is keyed by that UUID as text. In production the coercion produced `NaN` for every workspace, so the marking, the disconnect, the map delete and the log line never ran: a session already proved deaf stayed in the map, was beaten every 30 seconds, and kept reporting itself as connected. (Even past the guard it would have leaked, because `telegramClients.get(id)` looked up a number in a text-keyed map.) The rule is now `isValidWorkspaceId` in `services/telegram-listener.js`, next to the contract it belongs to; the handler keys everything by the id as it arrived; two tests and five pins cover it, and the shipped code fails all of them. No test had reached that closure because the listener tests fake the callback and the pool double matches on SQL text while ignoring parameters.
- [x] **The gate runs where it can be felt, and 12 tests keep it that way.** `npm test` is `npm run typecheck && node --test`, and the Render server `buildCommand` is `npm ci && npm run typecheck` - a type error now stops a deploy. `test/typescript-enforcement.test.js` pins the config (`include` must be `**/*.js` so a new directory cannot dodge it, `checkJs`/`noEmit` on, `strict` off, `test/` excluded), pins that both commands still wire it up, pins that **every `@typedef` is actually cast onto the parameter it documents** (a typedef nothing references reads like a contract while the checker goes back to guessing - which is exactly what happened, silently, to eight of them mid-task, all in signatures where the bag was not the first parameter), and pins the declarations against the code and the schema. `test/log-redaction.test.js` came out of the same work: typing the log line showed that its six-key redaction list and its single-console-writer property had no test at all. Eight mutations, each caught by exactly one test; and deleting one typedef's cast turns the checker back on at seven call sites, which is the evidence that the annotations are load-bearing rather than decorative.
- [x] **Two gaps, said out loud rather than hidden in a diff, plus one counted in the open.** **44 of the 320 declared properties are still `{any}` or `{Function}`** - every one of them a member this pass did not read the usage of, and each is the sort of line a later PR tightens with the call sites in view rather than a table applied across 41 files. A wrong type is louder than no type, which is the point of writing them.) `test/` is excluded - its 52 files build duck-typed fakes whose shapes are *meant* to violate the app types (a fake pool answering three queries is not a `PoolLike`), and teaching them to typecheck would be a different project with a different payoff. Attaching `UserRow`/`SignalRow`/`TradeRow` to them - the `overlayLiveBlocker`-style reads first, where a wrong field name is a wrong sentence shown to a trader - is the next increment, and it is the one that retires most of the 415 `Number(` calls by making the coercion visible from the column to the arithmetic.
- [x] **The ramp is measured, not wished for.** On top of this config, `--strictNullChecks` is **381** errors and full `--strict` is **1,986**: the next step is per-directory and per-file, with the error count for each directory named before it is taken, which is the only way a `strict: true` flag stops being an aspiration. `types/app.d.ts` is a declaration file, not a build input: `noEmit` is on, nothing compiles, nothing ships, and the enforcement test asserts the file contains no statement that could run.
